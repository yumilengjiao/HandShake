## 状态与转换

| 状态 | 进入/退出与行为 |
| --- | --- |
| DISABLED | 初始/紧急停止后；仅预览。人工启用后到 IDLE |
| IDLE / ARMING | 唯一稳定候选 wake_open 持续成立才授予 owner；多候选冲突不自动选人 |
| ACTIVE / CANDIDATE | 只接受当前 owner、有效模式、质量新鲜且过门限的词元；候选超时/改变则取消 |
| EXECUTING | 提交一次事件，生成唯一 event_id；连续控制另走允许状态 |
| WAIT_RELEASE | 同次动作禁止再次提交；明确中性/释放证据成立才允许重新武装 |
| COOLDOWN | 即使已释放仍满足最低间隔；只有冷却完成且已经释放才到 ACTIVE |
| SUSPENDED | 失跟、歧义、焦点/质量异常，冻结、释放、取消待执行，恢复后重新验证/唤醒 |

冷却不是释放证据；持续保持、分类抖动或一次低置信帧不得偷偷形成“新动作”。课程动态挥动的完整证据与参考时刻按 T05 定义，首次可用基于轨迹/时间的显式完成条件，P1 再用阶段头。

## 实施步骤

1. 状态机使用注入的单调/回放时钟，单一逻辑所有者顺序处理；协议与 mock 参数先用 T05/T07 的带 draft 配置，不把尚未完成的 T15 当实现前置。T15 提供校准，T28 联合冻结事件参数。600ms 唤醒、120ms 候选、150ms 释放、400ms 冷却仅作起点；静态唤醒不再重复叠加同一确认保持。
2. 每个候选绑定 owner、gesture、mode、model_version、context_epoch 和候选起点；失效清除，不能新旧模式拼证据。
3. 先检查源 stream/epoch、新鲜度、整帧多手冲突、当前质量与 ready，再进入控制权/启用/模式/类别/可选意图及释放/冷却判断。陈旧预测既不能执行，也不能推进候选、唤醒、释放计时。未训练 intent 头时字段为 None，不运行假意图门限；依靠明确协议并披露限制。
4. owner 与匿名轨迹绑定；交叉歧义立即挂起，不能靠 nearest hand 转移控制权。自然挥手与指令视觉相同仍可能误触，应在激活状态下测试而非声称模型读心。
5. 独立 stop 通道不等待模型或 UI 绘制：立即设停止位、增加 context_epoch、清队列/候选，由调度器安全路径执行 release_all，回 DISABLED；模式/模型/owner 变更及挂起同样使旧代际失效。执行提交与 stop 通过 T18 的串行提交闸门确定顺序，不能仅靠两处无锁布尔检查声称没有竞态。
6. 无预测/推理卡住也由时钟与健康事件驱动过期停止；不只在 update(prediction) 中检查失跟。重复停止应幂等，异常日志不能阻止释放。exit_pose 在 owner 可确认且输入可靠时可从候选/等待释放/冷却等状态退出，不被普通动作冷却阻挡；它仍不替代独立停止。
7. 首版计时使用连续新鲜有效证据；缺失、乱序或低质量清候选，不把断流前后的持有时间相加。挥动回程只能作为 WAIT_RELEASE 内的运动，明确中性停留后才重新武装；新增音量/光标模式按单独连续控制子状态接入，不套用“每帧一个离散事件”。

## 原生生命周期与移植约束

T36 的平台生命周期适配器将系统锁定/休眠、手机后台/锁屏、相机中断和权限撤销转换为明确健康/挂起事件，无新预测时也必须处理。恢复不自动启用或还原 owner，清旧窗口/候选后重新授权与唤醒；桌面演示应用在前台不等于移动 App 后台，两者不能共用简单“UI 失焦即停止”规则。

T37 非 Python 实现必须对照同一状态转移和 golden 时间轴，验证候选、持有、释放、冷却、超时与 stop 提交顺序；不在移动 UI 控制器复制第二套状态机。强杀进程没有退出回调保证；T38 的执行端需本地租约/watchdog，不能只依赖手机状态机通知。
