## 目标

不推翻现有 Python 核心，以有时间上限的技术验证选择原生 UI、桥接方式和可移植边界。原生为可安装、本地相机/生命周期、不依赖浏览器；不承诺一套二进制运行所有 OS，也不把手机限定成遥控器。

## 实施步骤

1. 更新 `docs/platform_support.md`：Windows、macOS、Linux X11/Wayland、Android、iOS/iPadOS 分列目标版本、CPU 架构、实机/工具链可得性；其他 OS 单列待评估。确定首个桌面演示平台和 Android/iOS 补测责任。
2. 限时比较“Flutter 等原生编译 UI + 插件”和“Qt 桌面 + 移动原生壳”等最多两条候选。验证首桌面的启动、mock 快照、相机帧通路、停止不阻塞、安装冒烟；核查手机相机/感知/推理 SDK、许可证与签名条件。未拿到设备只记录资料核查，不冒充手机实测。
3. 决策记录选定主路线、否决理由、平台插件缺口和回退。不可用的移动工具链不阻止保守桌面方案，但必须说明未来移植成本和未解决条件；不留下“任选 UI”让 T20 再做一轮无边界选型。
4. 定义相机、感知、Predictor、权限/生命周期、ActionBackend 的版本化边界。复用 T02 契约；需要跨语言绑定时生成/维护可校验 schema，不让 UI 直接改状态机或直接执行系统操作。
5. 冻结部署方式：桌面优先本机直接调用；不同语言 UI 用受控 IPC/FFI。手机本地运行时独立于 Python 训练栈；T37 再实现正式便携核心和模型转换。不强制 HTTP、云服务或数据库。
6. 约定模块/构建路径与依赖分组，保留 `handshake-core` 当前可用安装。平台特有库延迟加载；无该插件时返回明确不可用而非导入整个核心失败。原生子工程不被 Python 包发现误收入，不把 Android/iOS 工具链写进通用 Python 依赖。

## 交付与验收

产物为 `docs/native_stack_decision.md`、平台矩阵、接口/桥接草案、最小原型与实测记录；这些均为后续待实现产物。

- [ ] 有明确选型、范围、投入上限及失败回退，首桌面原型有安装/启动证据。
- [ ] Android 与 iOS/iPadOS 的本地运行路径、资产/算子/分发条件逐项记录；无设备项标待验证。
- [ ] 不改算法即可替换 mock 相机/执行适配器；未知平台不默认启用 live。
- [ ] 同一进程/跨进程方案都保留独立停止与核心单一调度所有权。
- [ ] 交给 T20 的是已确定的桌面 UI 路线；T37 的是可验证迁移计划，不是“所有 OS 已支持”。

本任务用合成数据及小模型形状探针即可完成，不等待 T16 正式权重，也不等待 T37 最终手机安装包，避免循环依赖。没有完成真实平台探针则仍为待验证。
