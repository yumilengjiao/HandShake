## 目标与输入

把“要实现哪些功能、在哪台机器演示、什么算完成”写成可签认记录。输入为总方案、课程通知、已做实验课题清单，以及两人的可用时间与设备；不把第 9/10 周直接转换为未经确认的公历日期。

## 具体步骤

1. 对照可核验的课程通知填写班级、方案汇报/答辩/报告截止时间和每人的可用投入；通知来源与待确认项留档。姓名、学号及通知原件放受控的 `private/course/`，公开任务用 A/B，正式提交的报告再按授权填入。建立实验课差异表：已有任务/数据/算法、本项目任务/自采数据/连续事件控制的新增内容。信息不足标“待确认”，不能宣称已排除重复。
2. 课程冻结为一个实测桌面平台的翻页闭环、原生 UI、自训 TCN、MLP 对照及安全测试；音乐和光标各作为独立 P1 任务。T36 前置验证原生路线，T37 将 Android/iOS 本机运行及其他桌面移植列为产品 P1，T38 配对控制可选 P2；不把手机永久推成无任务的愿景。
3. 在实际演示设备记录 OS/版本/ABI、桌面协议、相机、显示缩放、CPU、内存、训练设备、应用版本。另列 Android/iOS 真机、SDK/工具链/签名条件及负责人；其他 OS 按能力评估。按安装、相机、本地识别、应用内/外部控制分别列支持，不把“原生跨平台”解释为任意系统任意控制。
4. 确定单控制手、最大检测手数、界面/键盘停止路径与操作白名单。提前验证演示窗口获得焦点时停止键仍可用；仅 UI 内快捷键不能冒充独立停止。禁止默认启动后立即注入事件；默认 dry-run。焦点查询与全局停止接口不可用时，选择明确对象的应用内方案或其他已支持环境，不靠提权绕过。
5. 在测试之前冻结评价口径：分类与事件指标、有效测试时长、参考确认时刻、事件匹配窗口、性能采样方法。数值目标引用总方案但单列“目标/实测”，课程通过不等于全部研究数字达标。
6. 两人核对任务导航的课程关键路径与剩余时间，给必做任务填实际负责人和日期。按阶段退出条件推进，不用“第几天”代替完成证据。

## 验收与失败处理

- [x] 任何功能可明确归入必做、选做或后续研究，课程仍以翻页为主场景。
- [ ] 两人各有代码与实验职责，班级节点、平台未确认项有负责人。
- [ ] 无实测权限时采用 dry-run/应用内受支持接口，并明确演示平台；不绕过系统保护。
- [x] 验收口径在最终测试前留存版本；需求变更记录原因及影响到的任务。
