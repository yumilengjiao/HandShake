# 统一原生应用：实时手势翻页预览

现在从项目根目录只需启动一个应用：

```bash
uv run app
```

当本机 `artifacts/runs/latest.json` 指向已有完整导出/校准回执的模型时，启动器读取并校验该模型，默认进入“手势翻页”。**不会训练、重新导出、读取训练缓存或修改最新模型指针**。无完整模型时仍可打开普通界面，“手势翻页”明确显示尚不可用。

日常启动现在使用 Flutter **release** 模式，避免 debug 绘制和VM调试服务与实时感知争用资源。开发者需要热重载时，可通过高级入口 `uv run python scripts/run_native.py --debug ...` 显式启用；`uv run app --bundle <已构建程序>` 保持直接运行，不重编译。

初次安装需要 `uv run setup --camera`，以及可信的 `artifacts/perception/hand_landmarker.task`。Python 3.12、MediaPipe 0.10.21/OpenCV 4.11.0.86为当前感知环境。只有Linux原生宿主已验证。

## 窗口内操作

1. 点击右上角“手势翻页”（加载完整真实模型时已默认进入）。
2. **打开相机 / C**：显示实时画面；此时不允许翻页。
3. **启用手势 / E**：启动手势会话。
4. 只留一只手，掌心放在画面中央，**食指、中指伸直，无名指、小指弯曲并静止保持**。当前几何中立条件要求四指中1–3指伸直、其余弯曲；完全张掌或握拳不符合条件。本地演示接受足够置信度的 `NOG`（非手势）、`P1F`（单指）或 `P2F`（双指）作为中立类别，**不再要求两指手型必须被识别成 NOG**。按钮可用后点击或按 **O**。状态栏会区分手型不符、预热、识别过期、类别不符及置信度不足。
5. 保持静止，重新积累32帧历史及释放期。**向右抛动TRT翻下一页，向左抛动TLT翻上一页**；动作后回到中立，不长按连翻。
6. **停止控制 / 空格**：撤销手势授权，保留相机画面。
7. **关闭相机 / Esc**：停止控制并等待设备释放。字母键支持不按Shift，也支持Shift+C/E/O。

预览图像与动作证据使用独立时效：相机图像在750毫秒输入停滞期限内可继续显示，不再因为超过模型的150毫秒限制而交替发送空画面。前端保留同一解码器，跳过重复JPEG；短暂缺图不会重建黑屏，持续缺图或关闭相机仍清空画面。**旧画面不能用于获得选手或翻页权限**，模型证据的150毫秒检查保持不变。

左侧显示本应用实际页码与示例稿，右侧显示摄像头、模型类别、控制手和策略原因。这不是仅显示候选：满足模型与交互条件的事件经原有唯一调度器提交到本地演示后端，确实更改页码。

切换到“观测”或“人工演示”之前必须确认相机释放；未确认时留在原页。应用隐藏或失活也关闭相机，恢复前台后不自动开启或恢复控制。三个页面位于同一个Flutter窗口，不再需要另开OpenCV演示窗口。

当前统一页使用四页内置中文示例；暂未在该页提供自选PPT/图片导入。原 `handshake-demo --slides ...` 兼容入口仍保留，但正常使用统一预览不需要它。若旧演示窗口尚在使用摄像头，请先退出，避免跨进程设备占用。

## 模型与权限边界

- 保留真实模型、配套校准、15类词表、归一化和golden前向校验；合成诊断包不能获得真实翻页能力。
- **不改变旧的只读/影子协议**。原“观测”页面和 `--shadow` 仍不能翻页；“人工演示”仍只接受人工按钮/方向键。
- 新私有NDJSON子进程 `backend.native_gesture_cli` 复用 `DemoCameraWorker → LocalDemoSession → 原手势策略/调度器 → PresentationBackend`。UI不传手势类别、logits或上一页/下一页命令。
- UI请求绑定当前会话、递增命令号、相机代际和原始已展示快照；表面回执只在Flutter绘制后发送，不用新的快照替换旧请求。
- 仅容量一的帧槽与有界快照库存；相机画面不保存、不上传、不进入全局图片缓存。最多一个解码任务和一个待解码帧。
- 页面回执/父进程心跳与模型证据时效分别检查。失联、失跟、过期、停止和迟到结果不获得新动作权限。阻塞驱动释放未确认时不启动第二个worker。
- 既有置信度、位移、释放和冷却规则不放宽；不向操作系统注入按键，不控制PowerPoint/WPS。

外部交接模型仍可通过已有参数指定，无需本机训练缓存：

```bash
uv run app --package /path/to/model --sha256 <可信模型SHA> \
  --calibration /path/to/calibration.json --calibration-sha256 <可信校准SHA>
```

## `not_processed` / 判定原因闪动排查与修复

相机采用容量一的最新帧槽，消费不及时的旧帧会记为 `not_processed / latest_frame_replaced`。这是正常的**采集丢帧记录**，不是一次感知识别失败。此前模型会话把它写入当前分类、清掉选手资格、消耗待确认的选手请求，甚至传给选手后的预热检查，导致原因不断闪动、O很难可用或预热立即停止。

现在这类记录仅推进特征健康时钟：不覆盖最后一次完成的识别结果，不消耗选手请求，也不增加或破坏预热进度。**原始结果时间戳不变**，150毫秒过期检查与预热无进展超时仍有效；不断丢帧不能延长动作权限。真正的感知未处理（模型未加载、时间戳重复等）仍清除资格，并显示 `perception_not_processed:<具体原因>`。

后续回归：Python非训练检查1001通过、6未选中；Flutter110通过，静态分析与Linux发布构建通过。新增MLP/TCN测试复现“每隔一帧丢帧”的结果覆盖问题，并验证修复后的选手请求、32帧重新预热、实际页码变化以及持续无有效证据时的超时拒绝。这些是程序化链路测试，不是实拍识别成功率。

**当前现场问题仍未验收：用户在上述修改后仍反馈预览不可正常使用。** 不应把回归通过当作真实摄像头问题已解决；待另一台电脑复测，继续区分感知未处理、处理时延、模型类别/置信度和选手条件。

应用正在运行时，修改文件不会更新已导入代码的Python子进程。**必须完整退出旧窗口和启动命令，再运行 `uv run app`**；仅Flutter热重载或关闭/重开相机不足以加载后端修复。

## `warming_up` 长时间不结束：后续修复与诊断

先前丢帧修复只阻止模型会话用 `not_processed` 覆盖分类，仍漏掉了更底层的历史重置：旧采集丢帧记录超过150毫秒时，`OnlineClassifier.update()`会在进入未处理分支前清空历史。即使同批保留下来的图像仍新鲜、有效观测间隔也小于100毫秒，逐条回放旧账仍可能使预热永远从1开始。

相机worker现在直接处理同批保留下来的帧，由它将源/健康时钟推进到所有旧丢帧之后；没有保留帧时才处理最新的未处理记录。不伪造观测、不重复补帧，实际观测的间隔、质量、跨度和150毫秒时效检查保持不变。虚拟相机回归复现了“旧账170毫秒、保留图像120毫秒、有效帧间隔60毫秒”的失败，修改后第32个有效观测可进入预测。

手势页同时显示连续有效数与历史长度（两者可能分别为1/32和32/32）、源帧间隔、完成时帧龄及最近重置原因。新私有预览的可选 `diagnostics` 只含有界标量，不用于授权、不含图像，兼容没有该字段的旧测试快照。JPEG编码和该页遥测改为最多10Hz，感知/特征/模型仍按实际观测处理，不以10Hz休眠破坏采样契约。

这轮Python非训练回归1003通过，Flutter112通过，静态分析、Linux构建与当前真实motion包/校准只读校验通过。仍须现场确认；若预热继续重置，请提供新增的连续有效数、帧间隔、帧龄及最近重置原因，不能只凭 `warming_up` 判断已经解决。

## 静止单指 / 双指识别导致 O 不可用

旧条件一边要求部分手指伸直的几何中立姿态，一边只接受 `NOG` 分类。若模型将这个姿态识别为 `P1F/P2F`，即使预热完成也不能选手。现在仅 `LocalDemoSession` 的本地演示策略将 `NOG/P1F/P2F` 作为中立候选，选手和动作后释放使用同一规则；原影子/回放策略仍只接受 `NOG`，本地策略摘要单独绑定这项语义变化。

这不是将单指/双指映射成翻页：它们不会自行绑定控制手，也不生成动作。仍须显式 E、O，单手、几何中立、校准置信度、150毫秒时效、换代后32帧预热及静止释放均保留。只有 TLT/TRT 加满足条件的位移才可能翻页。界面补齐类别不符、静态类别置信度不足、请求过期及释放等待提示；旧的选手拒绝提示不再盖住新的可用状态或具体原因。

本次检查：`uv run check` **1058通过、6未选中**（13项既有警告）；Flutter **117通过**，`flutter analyze` 及Linux发布构建通过。MLP/TCN程序化链路覆盖三种中立类别、采集丢帧、原生选手请求与页码变化；负向检查覆盖低置信度、并列最高分、全部动态类别、过期和确认帧手型/类别变化。键盘组件检查覆盖 O / Shift+O、长按不重复请求；原公共策略仍只接受NOG。**没有打开真实相机或做模型训练，这些结果不代表现场 O 已验收；请完整重启应用后复测。**

## 持续提示“处理帧间隔超过上限”：当前值与历史原因分开

用户继续反馈预热数刚上升就回落，界面一直提示采样间隔超限。100毫秒是**实际处理观测的源帧间隔**上限，不是允许以10Hz休眠的目标；稳定30FPS约33毫秒，10FPS稍有抖动就会重置初始计数。画面刷新率不等于采集或感知速率。

进一步发现旧提示一直展示保留的 `_last_reset`，即使当前间隔已恢复正常。现在预热状态按当前 `source_gap_ms` 判断是否超限，历史原因另标“上次重置（历史记录）”。新增可选、有界、只读的 `capture_hz / perception_ms / model_ms`：分别是实际采集平均速率、本帧手部感知耗时和模型/策略耗时，不参与授权，也不修改模型时间戳、32帧要求、100/150毫秒门限。正常启动改用release模式降低额外开销；这不是已证明解决所有慢帧情况。

本机短测（只保留计数与耗时，未保存图像/关键点，未启用控制）：

- 640×480相机直接读取，原自动曝光动态帧率设置下45帧测得29.99Hz，间隔最大38.90ms；临时禁止曝光降低帧率后29.92Hz。结束已恢复原设置并释放相机，**没有据此永久修改驱动或断言曝光就是根因**。
- 8秒相机→MediaPipe→只读模型预览测得233帧、29.99Hz、消费者丢帧0；所有帧为`no_hand`。感知耗时P50/P95约21.47/38.18ms，源帧间隔最大37.44ms。此项**不能证明真实手部检测时的性能**。
- 当前真实模型包使用程序生成的手部观察做独立只读前向，预热完成，模型链路耗时P50/P95约2.29/5.47ms、最大7.79ms；不是实拍识别测试。

检查：Python非训练回归**1061通过、6未选中**；Flutter **118通过**，静态分析及Linux发布构建通过。需完整重启应用后再做真手复测；如当前仍持续超限，请提供同一时刻的当前帧间隔、采集FPS、感知/模型耗时与完成时帧龄，而不是只看保留的历史原因。
